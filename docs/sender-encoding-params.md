# Sender 编码参数说明（mode / profile / framerate）

本文档整理当前 sender 页面左侧菜单中 **mode / profile / framerate** 的真实含义。这里不按 UI 文案做泛泛解释，而是直接对应当前代码里的**编码参数**。

适用范围：
- `app/src/cpp/libcimbar/web/index.html`
- `app/src/cpp/libcimbar/web/main.js`
- `app/src/cpp/libcimbar/src/lib/cimb_translator/Config.h`
- `app/src/cpp/libcimbar/src/lib/cimb_translator/GridConf.h`

---

## 1. 总览：这三个参数分别控制什么

### mode
`mode` 是**编码版式 / 协议配置编号**。

它直接决定底层这些参数：
- `color_bits`：每个 cell 用多少 bit 表示颜色
- `symbol_bits`：每个 cell 用多少 bit 表示符号图案
- `ecc_bytes` / `ecc_block_size`：每个纠错块的 RS 冗余强度
- `image_size_x / image_size_y`：整张码图的目标分辨率
- `cell_size / spacing`：单个 cell 的尺寸和间距
- `fountain_chunks_per_frame`：每帧承载几个 fountain chunk
- `fountain_chunk_size`：每个 fountain chunk 的大小
- `legacy_mode`：是否走旧版颜色解释逻辑

也就是说，**mode 才是真正决定“这张码长什么样、每帧装多少数据、接收端按什么方式解”的核心参数**。

### profile
`profile` 是 sender 侧 UI 提供的一组**预设组合**。

它本身不是底层编码配置，而是把这些前台参数打包：
- 默认 `mode`
- 默认 `fps`
- 是否开启 `colorBalance`

当前代码里 profile 只是 sender 页的“快捷预设”。

### framerate
`framerate` 是 sender 页的**目标播放帧率**。

当前实现里本质是通过：
- `fps` -> `_interval = round(1000 / fps)` 毫秒

来控制下一张码图多久切一次。

它**不改变单帧编码容量**，只改变：
- 每秒能发出多少帧
- 相机能否稳定抓到完整帧
- 实际吞吐和稳定性之间的平衡

## 2. 当前 UI 暴露的 mode 列表

根据 `main.js`，sender 页当前暴露 6 个 mode：

- `4C` -> mode value `4`
- `Bu` -> mode value `66`
- `Bm` -> mode value `67`
- `B` -> mode value `68`
- `5x5` -> mode value `69`
- `5x5d` -> mode value `70`

此外代码里还有一个 `mode=8` 的 legacy 变体，但当前 UI 没有直接暴露。

## 3. mode 的精确定义

下面表格把每个 mode 对应的底层编码参数列出来。

### 3.1 参数字段含义

- `color_bits`：颜色编码 bit 数
- `symbol_bits`：图案编码 bit 数
- `bits_per_cell = color_bits + symbol_bits`
- `ecc_bytes / ecc_block_size`：每个块中用于纠错的冗余字节数 / 总块大小
- `capacity`：一整帧理论原始容量（字节）
- `payload_after_ecc`：扣掉 RS 冗余后真正可装 fountain 数据的字节数
- `chunks_per_frame`：每帧切成几个 fountain chunk
- `chunk_size`：单个 fountain chunk 字节数
- `legacy_mode`：旧版颜色模式，`color_mode=0`

> 注：`capacity / payload_after_ecc / chunk_size` 是按当前 `GridConf.h` 公式推出来的实际值。

### 3.2 mode 参数表

| UI 名称 | mode 值 | legacy | color_bits | symbol_bits | bits/cell | ecc_bytes / block | 图像尺寸 | cell 布局 | capacity | payload_after_ecc | chunks/frame | chunk_size |
| --- | ---: | --- | ---: | ---: | ---: | --- | --- | --- | ---: | ---: | ---: | ---: |
| 4C | 4 | 是 | 2 | 2 | 4 | 30 / 155 | 1024 x 1024 | 112 x 112, 8x8 cell | 6200 | 5000 | 10 | 500 |
| Bu | 66 | 否 | 2 | 4 | 6 | 33 / 168 | 736 x 637 | 80 x 69, 8x8 cell | 4032 | 3240 | 6 | 540 |

| B | 68 | 否 | 2 | 4 | 6 | 30 / 155 | 1024 x 1024 | 112 x 112, 8x8 cell | 9300 | 7500 | 12 | 625 |

## 4. 各 mode 的实际含义

### 4C (`mode = 4`)
特征：
- `legacy_mode = true`
- `color_bits = 2`
- `symbol_bits = 2`
- 每 cell 共 4 bit

含义：
- 这是**旧版 4-bit / 4-color** 模式。
- 颜色解释逻辑走 legacy 路径，`color_mode = 0`。
- 相比 `B` 系列，每个 cell 承载 bit 更少，所以单位面积容量较低。
- 每帧固定拆成 10 个 fountain chunk。

适合理解为：
- **兼容性/旧协议模式**，不是当前 sender 的主力高容量模式。

### Bu (`mode = 66`)
特征：
- `Conf8x8_micro`
- 8x8 cell
- 80 x 69 的较小网格
- 每 cell 6 bit
- 每帧 6 chunk

含义：
- 可以把它理解成 **B 系列的 micro / 小画幅版本**。
- 图像尺寸更小，单帧容量更低，但单 chunk 为 540 bytes。
- UI profile 里默认把它配到更高的 fps（R3 = 20 fps）。

适合理解为：
- **偏小画面、偏快切换** 的一档。

### Bm (`mode = 67`)
特征：
- `Conf8x8_mini`
- 8x8 cell
- 112 x 78 网格，16:9-ish 的横向画幅
- 每 cell 6 bit
- ECC 比 `B` 更重（36/179 vs 30/155）
- 每帧 12 chunk，单 chunk 429 bytes

含义：
- 可以理解成 **B 的 mini / 中间档**。
- 和 `B` 一样每 cell 6 bit，但单 chunk 更小、冗余更重。
- 它不是简单“缩小版”，而是整体参数重配，偏稳一些。

适合理解为：
- **比 B 更保守、容量更小的中间档**。

### B (`mode = 68`)
特征：
- `Conf8x8`
- 8x8 cell
- 112 x 112 正方形网格
- 每 cell 6 bit
- 每帧 12 chunk，单 chunk 625 bytes

含义：
- 这是当前 sender / receiver 体系里的**主力标准模式**。
- `2 color bits + 4 symbol bits = 6 bits/cell`，单帧有效容量与稳态都比较均衡。
- 当前很多逻辑默认都把 `68` 当默认值。

适合理解为：
- **标准默认档 / 最常用档**。

### 5x5 (`mode = 69`)
特征：
- `Conf5x5`
- 5x5 cell
- 162 x 162 网格
- 每 cell 4 bit
- ECC 40/216
- 每帧 12 chunk，单 chunk 880 bytes

含义：
- cell 更小，因此网格更密。
- 每 cell bit 数虽然低于 `B`（4 vs 6），但总 cell 数高很多，所以整帧容量更高。
- 对屏幕清晰度、浏览器缩放、相机解析度、采样稳定性要求也更高。

适合理解为：
- **高密度模式**，更吃显示和拍摄条件。

### 5x5d (`mode = 70`)
特征：
- `Conf5x5d`
- 5x5 cell
- 非完全对称网格：188 x 157
- `cell_spacing_x = 5`，`cell_spacing_y = 6`
- 每帧 16 chunk，单 chunk 735 bytes

含义：
- 这是 5x5 系列的另一种密排变体。
- `d` 可以理解为一个更激进/更密的版式变种：
  - 总 cell 数更多
  - 每帧 chunk 数也更多
  - 理论吞吐更高
- 但在真实屏摄场景里，对对焦、锐度、缩放和采样稳定性要求通常也更高。

适合理解为：
- **比 5x5 更激进的高密度模式**。

## 5. profile 的精确定义

当前 `main.js` 里 profile 定义如下：

| Profile | 对应 mode | fps | colorBalance |
| --- | --- | ---: | --- |
| R1 | Bm | 10 | false |
| R2 | B | 15 | false |
| R3 | Bu | 20 | false |
| X1 | 5x5 | 18 | false |
| X2 | 5x5d | 16 | false |

所以 profile 的实际意思不是“某个神秘算法级别”，而只是：

- `R1`：用 `Bm`，10 fps
- `R2`：用 `B`，15 fps
- `R3`：用 `Bu`，20 fps
- `X1`：用 `5x5`，18 fps
- `X2`：用 `5x5d`，16 fps

### 5.1 profile 命名的工程含义
当前代码里，profile 名字本身没有额外数学含义；它只是 UI 层预设名。

可以粗略这样理解：
- `R*`：B 系列 / 常规 8x8 系列预设
- `X*`：5x5 系列高密度预设

但这只是命名习惯，不是协议层字段。

### 5.2 手动切 mode 后 profile 会怎样
在 `main.js` 中：
- 如果你直接点 mode，且不是从 profile 调起，`_profile` 会被设成 `manual`
- 也就是说：
  - **profile 是预设入口**
  - **mode 才是最终生效的底层配置**

---

## 6. framerate 的精确定义

sender 页所谓 `framerate`，当前实现就是一个 UI 层的定时参数。

### 6.1 代码层含义
内部变量：
- `_interval`：两帧之间目标间隔，单位毫秒

换算关系：
- `fps = 1000 / interval`
- `interval = round(1000 / fps)`

例如：
- 10 fps -> 100 ms
- 15 fps -> 66 ms
- 20 fps -> 50 ms
- 18 fps -> 56 ms
- 16 fps -> 62 ms

### 6.2 它不会改变什么
`framerate` **不会改变**：
- 单帧编码容量
- chunk size
- ECC 强度
- 颜色 bit 数 / 符号 bit 数

这些都由 `mode` 决定。

### 6.3 它会改变什么
`framerate` 会影响：
- 每秒发多少帧
- 理论吞吐上限
- 手机相机能否稳定拍清每一帧
- 实际丢帧/混帧概率

因此：
- **mode 决定每帧装多少**
- **framerate 决定每秒发多少帧**

理论吞吐近似可以理解为：

`有效吞吐 ~= payload_after_ecc * fps`

但真实吞吐还要打折，取决于：
- 显示器刷新率
- 浏览器渲染稳定性
- 相机曝光/对焦
- 环境光
- 接收端解码成功率

## 7. colorBalance 是什么
当前 sender 代码里 profile 还带一个字段：
- `colorBalance`

当前预设全部是：
- `false`

它会传给：
- `Module._cimbare_next_frame(_colorBalance)`

native 侧对应行为：
- `false`：使用默认 `color_mode`
- `true`：会把颜色模式切到 `Config::color_mode() + 0x100`

也就是说它是**颜色输出策略的附加开关**，不是核心协议版本。

当前 UI 预设里没有启用它，所以对当前 sender 默认行为可以认为：
- **不做额外 color balance 处理**

---

## 8. mode / profile / framerate 三者关系

### 8.1 优先级关系
1. `profile` 先选出一个默认 `mode + fps + colorBalance`
2. 如果手动切 `mode`，则 profile 退化为 `manual`
3. 最终编码参数由 **mode** 决定
4. 播放速度由 **framerate / interval** 决定

### 8.2 一句话总结
- `mode`：**单帧怎么编码**
- `profile`：**一套 sender 预设**
- `framerate`：**多快切帧**

---

## 9. 对当前项目的实用解释

如果站在“电脑 HTML 发，手机 APK 收”的真实场景理解：

- `B / mode 68`
  - 是当前最标准、最稳妥的主力模式
- `Bm / mode 67`
  - 更保守一些
- `Bu / mode 66`
  - 小画幅、快节奏
- `5x5 / 5x5d`
  - 更高密度，更吃环境和设备
- `profile`
  - 只是给你快速选一组组合
- `framerate`
  - 太高时容易让手机只拍到过渡帧或不完整帧

所以在真实链路里：
- 想稳：优先看 `mode`
- 想快：再调 `framerate`
- 想一键切：用 `profile`
